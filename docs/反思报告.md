# 多 Agent 旅游规划系统反思报告

## 1. 项目概述

本项目从一个仅包含 `Hello, World!` 的 .NET 10 控制台项目开始，最终实现为 ASP.NET Core 多 Agent 旅游规划系统。

用户输入旅行目标后，主控 Agent 先让行程 Agent 选择核心城市，并与风险 Agent 并行工作；城市确定后，再并行启动酒店和交通 Agent。专业 Agent 调用工具取得事实结果，主控 Agent 计算初步方案并将费用交给预算 Agent。预算 Agent 判断是否超支，最后由主控 Agent 统一输出旅行计划。

## 2. 为什么选择自定义 Agent Loop

项目没有直接使用 Semantic Kernel 自动函数调用，而是使用 `HttpClient` 和自定义消息模型实现循环，原因如下：

1. 课程要求理解 Agent 内部原理，自写循环更容易逐行解释。
2. 可以清楚展示 assistant 工具调用与 tool Observation 的消息关系。
3. 对第三方框架版本依赖较少。
4. 可以统一接入 DeepSeek 在线客户端与离线确定性客户端。

代价是需要自行维护 API DTO、工具 Schema、消息序列化和异常处理。对于课程项目，这个复杂度可控，也更能体现对原理的掌握。

## 3. Agent Loop 逐行解读

核心代码位于 `DotNetAgentDev/Agents/AgentLoop.cs` 的 `RunAsync`。

### 3.1 准备工具和消息

```csharp
var tools = allowedTools.Select(_toolRegistry.GetDefinition).ToList();
var messages = new List<ChatMessage>
{
    new() { Role = "system", Content = BuildSystemPrompt(...) },
    new() { Role = "user", Content = BuildUserPrompt(context) }
};
```

逐句说明：

1. `allowedTools` 是当前专业 Agent 的工具白名单。
2. `GetDefinition` 只取得工具描述和 JSON Schema，不执行工具。
3. `system` 消息定义 Agent 的职责、边界和工具使用要求。
4. `user` 消息包含子任务、完整旅行需求与主控 Agent 共享上下文。
5. 旅行需求使用 JSON 包裹，减少自然语言解析歧义。

### 3.2 初始化工作记忆

```csharp
var trace = new List<AgentTraceStep> { ... };
var observations = new Dictionary<string, string>();
var toolCallCount = 0;
var finalAnswer = string.Empty;
```

逐句说明：

1. `trace` 保存用户可见的执行轨迹。
2. `observations` 保存工具名和最近一次结构化结果，供主控 Agent 解析。
3. `toolCallCount` 用于可观测性和答辩展示。
4. `finalAnswer` 在模型停止调用工具后写入。

### 3.3 有界推理循环

```csharp
for (var step = 0; step < _options.MaxSteps; step++)
{
    cancellationToken.ThrowIfCancellationRequested();
    var response = await _llmClient.CompleteAsync(messages, tools, cancellationToken);
```

逐句说明：

1. `for` 将推理限制在 `MaxSteps` 内，防止模型无限调用工具。
2. `ThrowIfCancellationRequested` 让浏览器取消请求时尽快停止后端工作。
3. `await` 不阻塞 ASP.NET Core 工作线程。
4. 每轮都发送完整消息历史和同一组工具定义，使模型看到之前的 Observation。

### 3.4 判断是否完成

```csharp
if (response.ToolCalls.Count == 0)
{
    finalAnswer = response.Content ?? "子任务已完成。";
    trace.Add(...);
    break;
}
```

逐句说明：

1. 没有 `tool_calls` 表示模型认为已经可以提交专业结论。
2. 空内容使用安全默认值，避免空引用。
3. 记录 `FinalAnswer` 轨迹。
4. `break` 结束循环并返回结果。

### 3.5 保存模型行动

```csharp
messages.Add(new ChatMessage
{
    Role = "assistant",
    Content = response.Content,
    ToolCalls = response.ToolCalls
});
```

工具调用本身也是 assistant 消息的一部分。必须原样加入历史，否则下一轮模型无法知道哪个调用对应后续工具结果。

### 3.6 执行工具

```csharp
foreach (var toolCall in response.ToolCalls)
{
    var result = await _toolRegistry.ExecuteAsync(
        toolCall.Name,
        toolCall.Arguments,
        cancellationToken);
    observations[toolCall.Name] = result.Content;
}
```

逐句说明：

1. 一次模型响应可能包含多个函数调用，因此使用 `foreach`。
2. `ToolRegistry` 检查工具是否已注册，再调用对应 C# 实现。
3. `Arguments` 是模型生成的 JSON 字符串，各工具负责反序列化为强类型输入。
4. 工具结果保存到工作记忆，主控 Agent 后续会解析为景点、酒店、交通等类型。

### 3.7 将 Observation 返回模型

```csharp
messages.Add(new ChatMessage
{
    Role = "tool",
    ToolCallId = toolCall.Id,
    Content = result.Content
});
```

逐句说明：

1. `role=tool` 表明内容不是用户或 assistant 自己生成的。
2. `ToolCallId` 与模型请求中的调用 ID 对应。
3. `Content` 是结构化 Observation。
4. 下一轮调用时，模型可以基于真实工具结果继续选择行动或结束。

### 3.8 步数上限与返回

```csharp
if (string.IsNullOrWhiteSpace(finalAnswer))
{
    finalAnswer = "达到最大推理步数...";
}

return new AgentRunResult(...);
```

逐句说明：

1. 如果循环因步数耗尽结束，则返回明确说明而不是静默失败。
2. 已获得的 Observation 仍保留，主控 Agent 可以继续使用。
3. 返回值同时包含结论、Observation、轨迹、调用次数和模型模式。

## 4. 多 Agent 的设计决策

### 选择专业分工而不是一个大 Prompt

单个 Agent 同时处理景点、住宿、交通、预算和风险时，工具列表过长，职责容易混乱。专业 Agent 有三个好处：

- Prompt 更短，任务边界明确。
- 工具白名单更小，误调用概率降低。
- 每个 Agent 的输入输出和错误更容易定位。

### 为什么预算 Agent 最后执行

预算不是独立事实查询，它依赖酒店选择、交通费用和实际活动门票。如果与其他 Agent 同时运行，只能使用猜测值。项目先确定核心城市，再取得行程、酒店、交通与风险结果，最后将费用上下文传给预算 Agent，体现了任务依赖关系。

### 为什么最终方案仍有确定性整合

LLM 输出结构可能不稳定。主控 Agent 使用强类型模型和确定性算法构建最终 `TravelPlan`，LLM 负责工具选择与专业结论，C# 负责预算计算、日期分配和格式约束。这样既保留 Agent 自主性，又保证 Web 页面总能收到合法结构。

## 5. Memory 设计反思

短期记忆直接使用消息列表和 Observation 字典，优点是简单直观。长期记忆使用 JSON 文件，适合单机课程项目，不需要额外数据库。

不足：

- JSON 文件不适合多实例部署。
- 当前没有用户认证，`UserId` 仅用于演示。
- 偏好提取采用分隔符规则，不具备语义归一化。

如果继续开发，会使用 SQLite 或 PostgreSQL，并加入向量检索来查找语义相近的历史偏好。

## 6. 离线模式的意义与限制

离线模式解决现场演示的三个风险：网络不可用、API 额度不足、模型输出偶发不稳定。它仍通过同一个 `AgentLoop` 生成 tool call、执行工具、产生 Observation，并非直接返回预制旅行计划。

限制是离线客户端按工具白名单顺序调用，不具备真正的自然语言推理能力。因此演示时应明确说明：

- 在线模式展示 LLM 自主选择。
- 离线模式展示系统架构与确定性容错。
- 两种模式共享工具、循环、主控协调和最终输出。

## 7. 错误处理与安全

- API Key 不写入源码或 Git。
- DeepSeek 失败时记录日志并降级。
- 工具参数错误转成失败 Observation。
- MCP 工具统一标记为只读、幂等、非破坏性，并默认只允许本机 Host 访问。
- 输入限制天数、人数和预算。
- 记忆文件损坏时跳过或重建。
- 旅游数据明确标记为模拟参考，避免用户误认为实时政策。

## 8. AI 工具使用情况

本项目使用 OpenAI Codex 辅助完成了以下工作：

- 分析课程要求和项目选题。
- 设计项目目录、领域模型、多 Agent 架构和工具 Schema。
- 生成后端、前端、测试与文档的第一版代码。
- 执行编译、API、桌面端和移动端浏览器验收。
- 使用官方 MCP C# SDK 实现并验证 Streamable HTTP 服务。
- 在验收中发现并修复加载遮罩显隐、预算输入步长两个问题。

项目成员需要在提交和答辩前完成以下人工工作：

1. 逐个阅读和运行所有模块。
2. 按团队实际分工修改本节，不能把 AI 生成内容描述为人工编写。
3. 用自己的语言解释 Agent Loop、工具调用、异步和 DI。
4. 根据现场 API 账户测试 DeepSeek 在线模式。
5. 修改模拟数据或界面时保留测试证据。

当前版本中，绝大部分新增代码和文档由 AI 生成初稿；项目成员负责需求确认、验收、理解、修订和最终责任。此说明需要在最终提交时保持真实。

## 9. 遇到的问题与改进

### 问题一：可观测性不能等同于思维链

需求希望展示 Thought，但直接展示模型私有推理既不可靠也不必要。项目改为展示系统生成的“决策摘要”，例如选择了哪个工具、参数摘要和 Observation，这些信息可核验。

### 问题二：实时 API 会降低演示稳定性

将景点、酒店、天气和风险知识放入本地 JSON，并实现离线 LLM 降级。未来可在工具内部替换为真实 API，而不修改 Agent。

### 问题三：LLM 结构化输出不稳定

最终 `TravelPlan` 由 C# 强类型整合，预算由确定性工具计算。即使模型最终文字不同，页面数据结构仍稳定。

### 问题四：前端原生校验细节

预算输入最初设置为 `min=1, step=100`，浏览器合法值从 1 开始递增，导致 12000 无法提交。浏览器端到端测试发现后将最小值改为 100。这说明编译和 API 测试不能替代真实 UI 验收。

## 10. 总结

本项目最重要的收获不是“让 LLM 生成一篇旅游攻略”，而是理解 Agent 如何把语言模型、控制循环、工具、记忆和确定性程序组合起来。LLM 负责判断下一步行动，工具提供可信数据，Agent Loop 维护状态，主控 Agent 处理依赖和冲突，C# 类型系统保证最终结果可以稳定展示。
