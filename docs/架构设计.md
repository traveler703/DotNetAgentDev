# 多 Agent 旅游规划系统架构设计

## 1. 设计目标

系统需要满足课程项目的五个核心要求：

1. 通过 HTTP 接入 DeepSeek 大语言模型。
2. 自主实现 ReAct Agent Loop。
3. 提供不少于 3 个自定义工具。
4. 具备短期工作记忆与长期用户记忆。
5. 提供可现场演示的 Web 用户界面。

同时采用多 Agent、单元测试和可观测执行轨迹作为加分项。

### 表现层

`Program.cs` 暴露计划生成、历史计划、用户记忆和运行状态 API。前端不依赖第三方框架，便于离线演示和解释。

### 应用层

`TravelPlanningService` 负责输入标准化和保存结果。`TravelCoordinatorAgent` 负责任务编排，不直接承担每个专业领域的工具选择。

### 领域层

领域模型使用不可变 `record`，包括旅行需求、每日行程、酒店、交通、预算、风险和执行轨迹。

### 基础设施层

DeepSeek、离线决策引擎、本地数据、JSON 记忆、MCP Server 和工具实现都位于基础设施边界内，可替换而不影响 Web 和领域模型。

## 3. 多 Agent 协作

```mermaid
sequenceDiagram
    actor User as 用户
    participant API as Web API
    participant C as 主控 Agent
    participant S as 专业 Agent
    participant L as Agent Loop
    participant M as LLM
    participant T as Tool Registry
    participant B as 预算 Agent

    User->>API: 提交旅行需求
    API->>C: PlanAsync(request)
    par 四个独立子任务
        C->>S: 行程规划
        C->>S: 酒店推荐
        C->>S: 交通估算
        C->>S: 风险检查
    end
    S->>L: RunAsync
    loop 直到完成或达到最大步数
        L->>M: messages + tool schemas
        M-->>L: tool call
        L->>T: ExecuteAsync
        T-->>L: observation
    end
    S-->>C: 专业结果
    C->>C: 构建每日计划并计算费用输入
    C->>B: 预算约束检查
    B-->>C: 是否超支与优化建议
    opt 总费用超过预算 110%
        C->>S: 重排行程、酒店和交通
        S-->>C: 返回预算约束后的专业结果
        C->>B: 第二次预算约束检查
        B-->>C: 返回修订预算
    end
    C-->>API: 统一 TravelPlan
    API-->>User: 展示结果和轨迹
```

主控 Agent 先并行启动行程与风险 Agent。行程 Agent 通过 `route_sort` 为国家或大区域选择通常不超过 3 个核心城市后，主控再将城市范围传给酒店与交通 Agent 并行执行。预算必须依赖前述实际估算，因此最后串行执行。该依赖顺序避免酒店、交通与最终行程使用不同城市。

## 4. ReAct 核心循环

`AgentLoop.RunAsync` 的状态由 `messages`、`trace`、`observations` 和步数共同组成：

```mermaid
stateDiagram-v2
    [*] --> Thought
    Thought --> AskLLM
    AskLLM --> Action: 返回 tool_calls
    Action --> Observation: 执行注册工具
    Observation --> AskLLM: 工具结果加入 messages
    AskLLM --> FinalAnswer: 没有 tool_calls
    AskLLM --> MaxSteps: 达到上限
    FinalAnswer --> [*]
    MaxSteps --> [*]
```

重要设计：

- 每个专业 Agent 只获得允许使用的工具 Schema。
- 工具调用必须通过 `ToolRegistry`，模型无法直接执行任意 C# 方法。
- Observation 作为 `role=tool` 消息和 `tool_call_id` 一起返回模型。
- 最大步数防止无限循环。
- 用户可见轨迹是系统操作摘要，不保存或展示模型私有思维链。

## 5. LLM 与降级设计

`ResilientLlmClient` 是业务层唯一依赖的 LLM 接口实现。

```mermaid
flowchart LR
    CALL["CompleteAsync"] --> KEY{"存在 API Key?"}
    KEY -->|否| OFF["OfflineLlmClient"]
    KEY -->|是| DS["DeepSeekLlmClient"]
    DS --> OK{"调用成功?"}
    OK -->|是| RESULT["返回模型响应"]
    OK -->|否| LOG["记录警告"]
    LOG --> OFF
    OFF --> RESULT
```

在线客户端直接使用 `HttpClient` 调用 `/chat/completions`，避免引入额外 SDK。离线客户端不会伪造自由文本模型，而是按允许工具列表依次生成规范函数调用，适合课堂演示和自动测试。

在线模式使用 DeepSeek SSE 流式响应。客户端按 chunk 聚合文本以及被拆分的工具名称、调用 ID 和 JSON 参数。应用层同时通过 `POST /api/plans/stream` 将带消息 ID 的 Agent 回复、工具调用、Observation 和模型增量推送到浏览器，并以聊天形式即时归并显示；旧的非流式 API 继续保留。已调用工具会从下一轮 Tool Schema 中移除，避免模型重复调用同一工具。

## 6. 工具设计

| 工具 | 输入 | 输出 | 数据来源 |
| --- | --- | --- | --- |
| `preference_memory` | 用户、当前偏好、目的地 | 历史偏好和日均预算 | JSON 长期记忆 |
| `attraction_search` | 目的地、偏好、数量 | 候选体验 | 本地知识库 |
| `route_sort` | 目的地、节奏、天数 | 城市顺序和每日密度 | 本地知识库 |
| `hotel_search` | 目的地、每晚预算、偏好 | 酒店列表 | 本地知识库 |
| `transport_estimate` | 出发地、目的地、天数、人数 | 交通费用与耗时 | 规则估算 |
| `weather_lookup` | 目的地、日期、天数 | 季节天气 | 本地知识库 |
| `risk_check` | 目的地、节奏、备注 | 风险列表 | 本地知识库 + 规则 |
| `budget_calculator` | 五类费用、预算 | 明细、余量、建议 | 确定性计算 |
| `travel_web_research` | 出发地、目的地、日期、主题 | 网页摘要、来源和发布时间 | Bing RSS + 官方域名优先过滤 |

每个工具都提供名称、自然语言描述和 JSON Schema。参数反序列化失败、未注册工具或执行异常都会返回失败 Observation，并写日志。

## 7. MCP Server

项目通过官方 `ModelContextProtocol.AspNetCore 1.4.0` 在 `/mcp` 提供
Streamable HTTP 服务。`TravelMcpTools` 将 9 个内部工具转换为 MCP 可发现的
强类型方法，但实际执行仍委托给同一个 `ToolRegistry`，因此内部 Agent 和外部
MCP 客户端不会产生两套业务逻辑。

```mermaid
flowchart LR
    CLIENT["MCP 客户端"] -->|"initialize / tools/list / tools/call"| ENDPOINT["/mcp"]
    ENDPOINT --> ADAPTER["TravelMcpTools"]
    ADAPTER --> REG["ToolRegistry"]
    REG --> TOOL["9 个旅游工具"]
    TOOL --> DATA["本地知识库 / JSON Memory / Web"]
```

服务器采用无状态模式。当前工具均为只读查询或确定性计算，MCP 元数据明确标记
`readOnly=true`、`idempotent=true`、`destructive=false` 和
`openWorld=false`。应用限制 Host 为本地回环地址，避免开发环境中的 DNS
重绑定风险。

## 8. Memory 设计

### 短期记忆

- LLM 的 `messages` 列表。
- 当前 Agent 的工具 Observation。
- 主控 Agent 的专业结果与费用上下文。

生命周期仅限一次规划。

### 长期记忆

- 每份完整 `TravelPlan` 单独保存为 JSON。
- `profiles.json` 聚合用户偏好、常去目的地、日均预算和计划数量。
- 写入使用 `SemaphoreSlim` 串行化，避免并发覆盖。
- JSON 使用 UTF-8 直接写入中文；启动时会迁移旧文件中的 `\uXXXX` 转义。

## 9. 错误处理与可观测性

- ASP.NET Core 入口执行输入边界校验。
- DeepSeek 非成功状态码转换为明确异常并自动降级。
- 工具异常由 `ToolRegistry` 捕获和记录。
- JSON 记忆损坏时跳过坏文件或使用空档案。
- `AgentTraceStep` 记录 Agent、阶段、标题、摘要与时间。
- SSE 实时推送 `progress`、`trace`、`delta`、`completed` 和 `error` 事件。
- MCP Server 日志记录协议握手、工具发现、工具调用耗时与错误状态。
- `Microsoft.Extensions.Logging` 记录计划、工具和模型状态。

## 10. 可扩展方向

1. 将搜索摘要进一步替换为航司、铁路、天气和签证机构的结构化实时 API。
2. 将 JSON 记忆替换为 SQLite / PostgreSQL。
3. 增加用户认证和多租户隔离。
4. 使用向量数据库实现旅游知识 RAG。
5. 为 MCP Server 增加认证、限流和部署配置。
6. 增加 Reviewer Agent 对最终计划进行反思和修订。
